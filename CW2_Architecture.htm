Basic Software Architecture

For a basic Unity XR Interaction Toolkit (XRIT) VR prototype, the simplest good way to write game logic is:

  1. Let XRIT handle tracking + grabbing + locomotion (do not rewrite it)
  2. Write your logic as small scripts that respond to events (select/activate) or input actions
  3. Keep a clean separation: Input to Intent to Gameplay

Below is a starter-friendly approach you can teach and reuse.

1) Minimal architecture for a VR prototype (logic-focused)

A. XR Rig (player) scripts

Attach to XR Origin / rig:

  • Player (health, score, ammo, your game state)
  • PlayerWeapons (what happens when you fire)
  • Optional: Haptics helper

B. Interactable object scripts

Attach to objects in the world:

  • GrabInteractable (usually XRIT's XRGrabInteractable + a tiny wrapper script)
  • Target / Enemy (take damage, die)
  • Pickup (ammo/health)

C. One coordinator (optional)

If the game has waves/spawning:

  • Spawner or WaveController (small and data-driven)

That is it. One screen worth of scripts.

2) Two ways to drive gameplay from XR controls

Option 1 (best for beginners): Use XRIT interaction events

This avoids deep Input System complexity.

Example: Gun is an interactable, and pulling trigger fires

  • You use an XRGrabInteractable on the gun object.
  • Add an XRBaseControllerInteractor for hands.
  • Use Activate events: when the held object is activated, call Fire().

Conceptually:

  • Grab event to gun is held
  • Activate event (trigger) to fire

This maps nicely to VR mental models.

Best practice logic rule:
Your gun script should not care about left/right controller bindings. It just implements:

  • OnGrabbed(hand)
  • OnReleased()
  • OnActivatePressed()
  • OnActivateReleased()

XRIT calls these via UnityEvents or event subscriptions.

Option 2 (more flexible): Use Input Actions like your repo does

Your repo's InputManager is an example of this: it listens to action started/canceled and calls gameplay methods like FireLaser(true/false) and FireCannon(press/release).

This is good when:

  • You want one place for all bindings
  • You have player abilities not tied to a held object (shield, teleport ray, menus)

Best practice logic rule:
Input should set intent (pressed/held/released), and gameplay scripts decide if the action is allowed.

3) The Input to Intent to Gameplay pattern

Step A: Input layer (XR controls) only sets intent

For a prototype, teach a tiny intent model:

  • FireHeld (bool)
  • TeleportHeld (bool)
  • MenuHeld (bool)

You can store these on a PlayerInputState component.

Step B: Gameplay reads intent in Update (or fixed tick)

Example decisions:

  • If FireHeld and weapon ready to shoot
  • If TeleportHeld to show teleport ray (or let XRIT do it)

This prevents:

  • spaghetti callbacks everywhere
  • hard-to-debug timing issues

It also makes it trivial to add:

  • pause menu disabling inputs
  • game not started yet gating
  • tutorial lockouts

4) Basic VR shooting: what to teach as correct logic

A. Use press vs release explicitly

VR triggers are analog-ish, but for prototypes:

  • started = pressed
  • canceled = released

Your repo does a solid pattern for a charge weapon:

  • press starts charging
  • release fires (if charged)

B. Avoid Instantiate per shot (pooling)

Even for a prototype, teach this early because VR comfort is sensitive to stutter:

  • Pre-create N bullets (10-50)
  • Reuse inactive ones

You do not need a complicated pool class at first, just:

  • a List<Bullet>
  • find inactive
  • reset & reuse

(Your repo's SpawnManager already demonstrates this approach.)

C. Keep weapon code independent from input code

A weapon script should expose:

  • BeginFire()
  • EndFire()
  • TryFireOnce()

Then input can call those methods whether the source is:

  • trigger action
  • UI button
  • automated turret
  • network replay

5) Locomotion: prototype best practice

For student prototypes:

  • Use XRIT's built-in Teleportation Provider or Continuous Move Provider
  • Your code should only:
    • enable/disable locomotion modes (for example, when in menus)
    • display comfort UI (optional)

Do not write your own character controller unless the assignment is specifically about locomotion.

6) A small wave prototype state machine

If you want a simple wave loop, teach 3 states:

  • Idle (waiting for player to start)
  • Spawning (spawn enemies on a timer until count reached)
  • Clearing (wait until enemies alive = 0)

This is enough for coursework and prevents boolean soup.

7) Five rules to drill into students for VR prototype logic
  1. XRIT does interactions; you do game rules.
  2. Input is not gameplay (input sets intent; gameplay enforces rules).
  3. Pool frequently spawned objects (bullets, enemies, VFX).
  4. Make states explicit (enum beats multiple booleans).
  5. Keep Update small (VR needs stable frame time).

 

Escape Room Architecture

For an escape-room VR prototype in Unity XR Interaction Toolkit (XRIT), the cleanest starter game-logic approach is to treat the whole game as:

  • Interactables (things you can grab/press/turn)
  • Receivers (locks, doors, drawers, keypads)
  • Puzzle logic (a small amount of state: solved/unsolved, code entered, key inserted)

You do not need a big manager architecture. You need small scripts with clear responsibilities, mostly event-driven.

1) Minimal set of scripts (student-friendly)

A. Interaction wrappers (per object)

  • GrabItem (optional wrapper around XRGrabInteractable)
  • PressButton (uses XRBaseInteractable.activated)
  • SocketKey (uses XRSocketInteractor events)
  • TurnDial (uses rotation to produce a value)

B. Puzzle logic (per puzzle)

  • DoorLock (listens for key/socket or code solved; opens door)
  • CombinationLock (checks dial values; raises Solved event)
  • Keypad (collect digits; validates code; raises Solved event)

C. Feedback helpers (optional but good)

  • HapticsOnEvent
  • PlaySoundOnEvent
  • HighlightOnHover (simple hover glow)

That is enough for a whole prototype.

2) Best-practice logic: Interactable sends event, puzzle decides

Teach students this rule:

Interactable scripts should report what happened (Pressed, Inserted, Turned-to-value). Puzzle scripts decide what it means (correct code, unlock door, reveal clue).

This prevents hard-coding puzzle rules into buttons/dials and makes puzzles reusable.

3) Use XRIT events instead of direct InputActions

For escape rooms, most actions are object-centric (grab, press, insert), so XRIT events are perfect:

Common XRIT events to use

  • Hover: player is pointing at it (for highlight)
  • Select: grabbed or selected
  • Activate: use action while held (trigger squeeze typically)
  • Socket select: object inserted into a socket

This avoids writing a central InputManager for the prototype.

4) Concrete patterns to teach

Pattern A: Pressable button (event-driven)

Student goal: Press a physical button to toggle something or send a signal.

How:

  • Put an XRBaseInteractable (or XRSimpleInteractable) on the button object.
  • Subscribe to activated (or use the inspector UnityEvent).
  • Button script raises OnPressed.

Puzzle scripts listen to OnPressed.

Best practices:

  • Debounce (ignore presses within 0.2s).
  • Keep the button script generic (I was pressed), not open door.

Pattern B: Key + lock using XRSocketInteractor

Student goal: Put a key in a keyhole; door unlocks.

How:

  • Door has an XRSocketInteractor at the keyhole.
  • Key is an XRGrabInteractable.
  • When socket selects the key, mark the lock satisfied.

Best-practice logic detail:

  • Identify key by ID (string or ScriptableObject), not by object name.
  • Lock checks ID, then unlocks.

Pattern C: Dial combination based on rotation

Student goal: Turn 3 dials to the right numbers.

How:

  • Each dial exposes a CurrentValue (0-9) derived from rotation.
  • CombinationLock reads all dials and compares to solution.

Best practices:

  • Quantize rotation into steps (snap to 36 degrees for 10 digits).
  • Emit OnValueChanged(int) only when the snapped value changes.

Pattern D: Keypad / code entry

Student goal: press digit buttons; validate code.

How:

  • Each digit button emits OnDigitPressed(int).
  • Keypad accumulates digits, updates display, validates.

Best practices:

  • Separate UI display from validation logic.
  • Keep code in a config object (ScriptableObject) so designers can change it.

5) How to structure puzzle state (simple state machines)

Teach explicit state but keep it tiny:

Example: Door

  • Locked
  • Unlocked
  • Open

Door transitions:

  • Locked to Unlocked when prerequisites satisfied
  • Unlocked to Open when handle pressed, door grabbed, or automatic open trigger

This makes bugs easier to reason about than scattered booleans.

6) Pooling and performance (what matters, what does not)

Escape rooms typically do not spawn 100 bullets, so pooling is less central than in wave shooters.

Still worth teaching:

  • Avoid frequent Instantiate/Destroy for UI popups or sparkle VFX
  • Prefer enabling/disabling objects
  • Use one-shot audio sources carefully (or a tiny audio helper)

Do not over-engineer pools for a beginner escape room.

7) Recommended first puzzle sequence for teaching
  1. Button turns on a light (press event + feedback)
  2. Key socket unlocks a drawer (socket event + lock)
  3. Drawer contains a dial clue (simple progression)
  4. 3-dial combination unlocks final door (state machine + quantized rotation)

This covers all key VR interactions without heavy systems.

  • the event wiring (who listens to whom) in the simplest teachable form

Software Architecture

This is a Unity (C#) XR game project organised around a central manager architecture (a GameManager that wires together multiple subsystem managers), plus scene entities (player, enemies, projectiles) and wave/spawn gameplay logic.

High-level structure (Unity project layout)

At the repo root you have the standard Unity folders: Assets/, Packages/, and ProjectSettings/, indicating this is a Unity project rather than a multi-project .NET solution. The primary architecture documentation is in README.md, which contains a Mermaid class diagram of the core runtime components.

Core runtime architecture: Manager-centric orchestration

1) GameManager as the composition root / service locator

GameManager (a MonoBehaviour) owns static references to the major subsystems and key game state:

  • Static subsystem references: ControllerManager, SpawnManager, GUIManager, AudioManager, VisualEffectManager, PerkManager, SpecialManager
  • Key game state: mainLoadout, gameInProgress
  • Also finds/links: WaveManager (via FindObjectOfType) and PlayerEntity (by locating the XR Origin)

In practice, this is a central orchestration + global-access pattern (static fields), where GameManager initialises and exposes other managers for broad use.

2) Input layer: InputManager to gameplay controllers/entities

InputManager is responsible for XR input setup using XRIDefaultInputActions, and then forwarding actions to:

  • ControllerManager (hand/controller functionality, toggles like plasma cannon referenced in the diagram)
  • PlayerEntity (player-centric actions)

So the flow is effectively: XRI Input Actions to InputManager to (ControllerManager / PlayerEntity).

3) Encounter loop: WaveManager drives progression, SpawnManager materialises entities

The gameplay loop is split into:

  • WaveManager: owns wave state (waveIndex, spawnIndex, playerScore, hostilesDefeated, missionFails) and the waveArray configuration (WaveDetails[]). It:
    • starts encounters (BeginEncounter)
    • reacts to kills (EnemyDefeated(type))
    • updates timing/state (Update, DelaySpawn, ResetRecentEnemyDefeats)
    • ends the run (EndGame)
    • triggers UI/audio/special-menu hooks via GUIManager, AudioManager, SpecialManager, etc.
  • SpawnManager: handles where/how objects appear:
    • spawn locations (Transform[] spawnArray)
    • environment hooks (Animator[] doorAnimators)
    • tracks active enemies (static int activeHostiles, plus List<EnemyEntity> enemyList)
    • spawns enemies and multiple projectile types (player, turret, seeker)

This is a fairly classic separation: WaveManager decides when/what, SpawnManager performs the instantiation/pooling/spawn mechanics.

4) Data/config: serializable wave definitions

Two serializable structs model content:

  • WaveDetails: contains SpawnSettings[], maxEnemyCount, waveTrigger
  • SpawnSettings: contains enemyTypeToSpawn, spawnLocationIndex, spawnCooldown

So waves are data-driven via arrays of settings, likely authored in the Unity Inspector.

Key entities (domain objects)

The diagram calls out these main entity types:

  • PlayerEntity
  • EnemyEntity
  • ProjectileController and PlayerProjectileController

These are the runtime objects the managers create/control.

Scene composition (GameObjects and components)

The README diagram suggests two key GameObjects:

  • GO_GameManager_Object: holds GameManager and the various subsystem managers as components
  • GO_XR_Origin: holds the PlayerEntity component

That implies a scene setup where manager singletons live together on one object, while the XR rig/origin owns the player logic.

A good way to teach this repo's architecture to university students is to frame it as Unity XR gameplay as a set of cooperating runtime systems, each system has a single responsibility, communicates through clear contracts, and is driven by Unity's update loop without turning everything into one giant script.

This project is a Unity3D XR application (standard Unity layout: Assets/, Packages/, ProjectSettings/). Within Assets/ there is an explicit code organisation under Assets/Scripts/ with folders like Managers/, Player/, EntityScripts/, Interaction/, and ScriptableObjects/, which is exactly what you would want students to do: separate concerns by domain rather than dumping everything into one folder.

Below I will explain the architecture in a best-practice teaching style, while also being honest about what the repo currently does (based on its README class diagram).

1) The architectural style: Runtime systems + entities in Unity XR

Two kinds of code you almost always have in a VR Unity game

  1. Systems (Managers)
    These coordinate rules and flow (spawning, waves, UI updates, audio triggers, effects, input routing).
    They often live for the whole scene (or whole app).
  2. Entities (Player/Enemy/Projectiles/Interactables)
    These represent objects in the world that have behaviours and state.

This repo follows that pattern clearly:

  • Managers: GameManager, SpawnManager, WaveManager, GUIManager, AudioManager, VisualEffectManager, PerkManager, SpecialManager, ControllerManager, InputManager
  • Entities: PlayerEntity, EnemyEntity, projectiles like ProjectileController / PlayerProjectileController

2) Scene composition: how Unity objects are wired

The README diagram describes two important GameObjects:

GO_GameManager_Object

A composition root GameObject holding multiple manager components:

  • GameManager
  • SpawnManager
  • InputManager
  • ControllerManager
  • GUIManager
  • AudioManager
  • VisualEffectManager
  • PerkManager
  • SpecialManager

Teaching point: this is a common pattern in Unity, group global systems on one object so they are easy to find, configure, and keep alive.

GO_XR_Origin

The XR rig/origin object that contains the PlayerEntity component.

Teaching point: in XR, the XR Origin is effectively the player body + tracking space. Keeping player logic attached here is good practice (movement, health, ability usage, etc.).

3) The GameManager as composition root pattern (and why it matters)

In the diagram, GameManager:

  • is a MonoBehaviour
  • stores static references to other managers/entities:
    • ControllerManager, SpawnManager, PlayerEntity, GUIManager, GameSettings, WaveManager, AudioManager, VisualEffectManager, PerkManager, SpecialManager
  • performs setup in Awake() and InitialiseManager()
  • provides high-level app commands: ReturnMainMenu(), RestartGame()

Teaching point: Composition root vs. God object

Good intention: central place where references are collected and setup happens.
Risk: if GameManager becomes the place where all gameplay logic lives, it becomes a God object.

In this repo, it is not just wiring: it also holds global state (gameInProgress, mainLoadout). That is okay, but students should learn the rule:

Let GameManager coordinate systems, not replace them.

Best practice logic coding advice

If you teach from this codebase, recommend:

  • GameManager should set up references and own high-level state transitions (menu to gameplay to results).
  • Wave logic stays in WaveManager.
  • Spawn logic stays in SpawnManager.
  • UI update logic stays in GUIManager.
  • Do not let GameManager.Update() become the whole game.

4) Input architecture in XR: InputManager as an input boundary

The diagram shows:

  • InputManager owns XRIDefaultInputActions customInput
  • lifecycle: Awake(), InitialiseInput(), OnEnable(), OnDisable()
  • it calls into ControllerManager and PlayerEntity

Teaching point: Separate input reading from game actions

In VR, input complexity is high (multiple controllers, gestures, interactions, locomotion modes). Best practice is:

  • Input layer (InputManager): reads hardware/controller state via the Input System / XRI actions.
  • Gameplay layer (PlayerEntity / ControllerManager): exposes intent-based methods like TryFire(), ToggleTool(), Grab(), Teleport(), etc.

That way, you can:

  • remap input without rewriting gameplay logic,
  • simulate input for testing,
  • support multiple control schemes.

XR-specific best practices to teach

  • Avoid doing heavy logic in input callbacks; instead set intent flags or call small methods.
  • Debounce actions (for example, trigger press vs. hold).
  • Prefer action-based input (XRI default input actions) over polling controller state manually.

5) Encounter loop design: WaveManager + SpawnManager

This is the heart of the gameplay.

WaveManager = gameplay progression + scoring + pacing

It owns:

  • waveIndex, spawnIndex
  • playerScore, hostilesDefeated
  • static int missionFails
  • configuration: WaveDetails[] waveArray

And key behaviours:

  • BeginEncounter()
  • EnemyDefeated(type)
  • internal update loop: Update()
  • coroutines: DelaySpawn(), ResetRecentEnemyDefeats()
  • EndGame()

Teaching point: This is a classic game loop controller:

  • Maintains the state machine of the encounter.
  • Emits/requests actions from other systems (spawn next enemy, update UI, play audio).

SpawnManager = instantiate/pool & place objects

It owns:

  • Transform[] spawnArray (spawn points)
  • Animator[] doorAnimators (environmental feedback tied to spawns)
  • List<EnemyEntity> enemyList (tracking/pooling)
  • static int activeHostiles (global count)

And spawns:

  • SpawnEnemy(spawnSettings)
  • multiple projectile spawn methods: player/turret/seeker projectiles

Teaching point: separate decide what spawns from how it spawns:

  • WaveManager should decide what and when.
  • SpawnManager should decide where and how (including pooling, effects, door animations, etc.).

Why this matters in VR best-practice coding

VR performance is unforgiving. Spawning objects can cause:

  • GC allocations to stutter
  • CPU spikes to missed frames to discomfort

So students should be taught to implement:

  • pooling for enemies/projectiles/VFX,
  • simple, data-driven spawn rules,
  • careful use of coroutines/timers over heavy per-frame logic.

  • SpawnSettings is a Serializable struct containing:
    • EnemyType enemyTypeToSpawn
    • int spawnLocationIndex
    • float spawnCooldown

Teaching point: Data-driven beats hard-coded

This is excellent to teach: your content (waves) should be editable without rewriting code.

Best practice suggestions for students:

  • Prefer ScriptableObject assets for more complex wave definitions (versionable, reusable, can include references).
  • Keep the runtime logic generic: read a definition, execute it.

7) Cross-cutting systems: UI, audio, VFX, perks, specials

The diagram indicates these interactions:

  • WaveManager triggers:
    • GUIManager for UI updates
    • AudioManager for sound/music
    • SpecialManager for a special menu
    • ControllerManager for toggles (plasma cannon)
    • GameSettings for score persistence

Teaching point: avoid direct spaghetti calls as projects grow

Right now, the architecture appears to be direct references (and many are static). That works for coursework scale, but for best practices, teach:

  • Use events/messages for state changed notifications:
    • OnWaveStarted(waveIndex)
    • OnEnemyDefeated(enemyType)
    • OnScoreChanged(newScore)
  • UI/audio/VFX subscribe to events rather than being called from everywhere.

This reduces coupling and makes systems independently testable.

8) A best-practice mental model students can follow (practical checklist)

When writing logic code for Unity XR, teach students to ask:

  1. Is this code a System or an Entity?
    • If it coordinates gameplay flow: System (Manager).
    • If it lives on a world object: Entity behaviour.
  2. What owns the state?
    • Wave state belongs in WaveManager.
    • Spawn state belongs in SpawnManager.
    • Player combat state belongs in PlayerEntity / weapon controllers.
  3. Where does input end and gameplay begin?
    • InputManager reads input.
    • PlayerEntity executes game actions.
  4. What happens per-frame vs. event-driven?
    • Prefer event-driven.
    • Keep Update() short and predictable.
  5. Will this allocate memory at runtime? (VR performance)
    • Avoid new allocations in Update().
    • Pool frequently spawned objects.
