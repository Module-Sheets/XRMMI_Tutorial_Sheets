For an escape-room VR prototype in Unity XR Interaction Toolkit (XRIT), the cleanest “starter” game-logic approach is to treat the whole game as:

  • Interactables (things you can grab/press/turn)
  • Receivers (locks, doors, drawers, keypads)
  • Puzzle logic (a small amount of state: solved/unsolved, code entered, key inserted)

You do not need a big manager architecture. You need small scripts with clear responsibilities, mostly event-driven.

1) Minimal set of scripts (student-friendly)

A. Interaction wrappers (per object)

  • GrabItem (optional wrapper around XRGrabInteractable)
  • PressButton (uses XRBaseInteractable.activated)
  • SocketKey (uses XRSocketInteractor events)
  • TurnDial (uses rotation to produce a value)

B. Puzzle logic (per puzzle)

  • DoorLock (listens for key/socket or code solved; opens door)
  • CombinationLock (checks dial values; raises “Solved” event)
  • Keypad (collect digits; validates code; raises “Solved” event)

C. Feedback helpers (optional but good)

  • HapticsOnEvent
  • PlaySoundOnEvent
  • HighlightOnHover (simple “hover glow”)

That’s enough for a whole prototype.

2) Best-practice logic: “Interactable sends event, puzzle decides”

Teach students this rule:

Interactable scripts should report what happened (Pressed, Inserted, Turned-to-value).
Puzzle scripts decide what it means (correct code, unlock door, reveal clue).

This prevents hard-coding puzzle rules into buttons/dials and makes puzzles reusable.

3) Use XRIT events instead of direct InputActions (simpler for escape rooms)

For escape rooms, most actions are object-centric (grab, press, insert), so XRIT events are perfect:

Common XRIT events to use

  • Hover: player is pointing at it (for highlight)
  • Select: grabbed or selected
  • Activate: “use” action while held (trigger squeeze typically)
  • Socket select: object inserted into a socket

This avoids writing a central InputManager for the prototype.

4) Concrete patterns to teach

Pattern A: “Pressable button” (event-driven)

Student goal: Press a physical button to toggle something or send a signal.

How:

  • Put an XRBaseInteractable (or XRSimpleInteractable) on the button object.
  • Subscribe to activated (or use the UnityEvent in the inspector).
  • Button script raises OnPressed.

Puzzle scripts listen to OnPressed.

Best practices:

  • Debounce (ignore presses within 0.2s).
  • Keep the button script generic (“I was pressed”), not “open door”.

Pattern B: “Key + lock” using XRSocketInteractor

Student goal: Put a key in a keyhole; door unlocks.

How:

  • Door has an XRSocketInteractor at the keyhole.
  • Key is an XRGrabInteractable.
  • When socket selects the key, you mark the lock satisfied.

Best-practice logic detail:

  • Identify key by ID (string or ScriptableObject), not by object name.
  • Lock checks ID, then unlocks.

This is a great early lesson in avoiding fragile comparisons.

Pattern C: “Dial combination” based on rotation

Student goal: Turn 3 dials to the right numbers.

How:

  • Each dial exposes a CurrentValue (0–9) derived from rotation.
  • CombinationLock reads all dials and compares to solution.

Best practices:

  • Quantize rotation into steps (snap to 36° for 10 digits).
  • Emit OnValueChanged(int) only when the snapped value changes.

Pattern D: “Keypad / code entry”

Student goal: press digit buttons; validate code.

How:

  • Each digit button emits OnDigitPressed(int).
  • Keypad accumulates digits, updates display, validates.

Best practices:

  • Separate UI display from validation logic.
  • Keep code in a config object (ScriptableObject) so designers can change it.

5) How to structure puzzle state (very simple state machines)

Teach students “explicit state” but keep it tiny:

Example: Door

  • Locked
  • Unlocked
  • Open

Door transitions:

  • Locked → Unlocked when prerequisites satisfied
  • Unlocked → Open when handle pressed / door grabbed / automatic open trigger

This makes bugs easier to reason about than scattered booleans.

6) Pooling & performance (escape rooms: what matters, what doesn’t)

Escape rooms typically don’t spawn 100 bullets, so pooling is less central than in wave shooters.

Still worth teaching:

  • Avoid frequent Instantiate/Destroy for “UI popups” or “sparkle VFX”
  • Prefer enabling/disabling objects
  • Use one-shot audio sources carefully (or a tiny audio helper)

But don’t over-engineer pools for a beginner escape room.

7) A recommended “first puzzle” sequence for teaching

  1. Button turns on a light (press event + feedback)
  2. Key socket unlocks a drawer (socket event + lock)
  3. Drawer contains a dial clue (simple progression)
  4. 3-dial combination unlocks final door (state machine + quantized rotation)

This covers all key VR interactions without heavy systems.
