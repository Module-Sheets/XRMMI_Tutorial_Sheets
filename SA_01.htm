Core runtime architecture: Manager-centric orchestration

1) GameManager as the composition root / service locator

GameManager (a MonoBehaviour) owns static references to the major subsystems and key game state:

  • Static subsystem references: ControllerManager, SpawnManager, GUIManager, AudioManager, VisualEffectManager, PerkManager, SpecialManager
  • Key game state: mainLoadout, gameInProgress
  • Also finds/links: WaveManager (via FindObjectOfType) and PlayerEntity (by locating the XR Origin)

In practice, this is a central orchestration + global-access pattern (static fields), where GameManager initialises and exposes other managers for broad use.

2) Input layer: InputManager → gameplay controllers/entities

InputManager is responsible for XR input setup using XRIDefaultInputActions, and then forwarding actions to:

  • ControllerManager (hand/controller functionality, toggles like “plasma cannon” referenced in the diagram)
  • PlayerEntity (player-centric actions)

So the flow is effectively: XRI Input Actions → InputManager → (ControllerManager / PlayerEntity).

3) Encounter loop: WaveManager drives progression, SpawnManager materialises entities

The gameplay loop is split into:

  • WaveManager: owns wave state (waveIndex, spawnIndex, playerScore, hostilesDefeated, missionFails) and the waveArray configuration (WaveDetails[]). It:
    • starts encounters (BeginEncounter)
    • reacts to kills (EnemyDefeated(type))
    • updates timing/state (Update, DelaySpawn, ResetRecentEnemyDefeats)
    • ends the run (EndGame)
    • triggers UI/audio/special-menu hooks via GUIManager, AudioManager, SpecialManager, etc.
  • SpawnManager: handles where/how objects appear:
    • spawn locations (Transform[] spawnArray)
    • environment hooks (Animator[] doorAnimators)
    • tracks active enemies (static int activeHostiles, plus List<EnemyEntity> enemyList)
    • spawns enemies and multiple projectile types (player, turret, seeker)

This is a fairly classic separation: WaveManager decides when/what, SpawnManager performs the instantiation/pooling/spawn mechanics.

4) Data/config: serializable wave definitions

Two serializable structs model content:

  • WaveDetails: contains SpawnSettings[], maxEnemyCount, waveTrigger
  • SpawnSettings: contains enemyTypeToSpawn, spawnLocationIndex, spawnCooldown

So waves are data-driven via arrays of settings, likely authored in the Unity Inspector.

1) The architectural style: “Runtime systems + entities” in Unity XR

Two kinds of code you almost always have in a VR Unity game

  1. Systems (Managers)
    These coordinate rules and flow (spawning, waves, UI updates, audio triggers, effects, input routing).
    They often live for the whole scene (or whole app).
  2. Entities (Player/Enemy/Projectiles/Interactables)
    These represent objects in the world that have behaviours and state.

This repo follows that pattern clearly:

  • Managers: GameManager, SpawnManager, WaveManager, GUIManager, AudioManager, VisualEffectManager, PerkManager, SpecialManager, ControllerManager, InputManager
  • Entities: PlayerEntity, EnemyEntity, projectiles like ProjectileController / PlayerProjectileController

2) Scene composition: how Unity objects are “wired”

GO_GameManager_Object

A “composition root” GameObject holding multiple manager components:

  • GameManager
  • SpawnManager

Teaching point: this is a common pattern in Unity—group “global systems” on one object so they’re easy to find, configure, and keep alive.

Teaching point: in XR, the XR Origin is effectively “the player body + tracking space”. Keeping player logic attached here is good practice (movement, health, ability usage, etc.).

3) The “GameManager as composition root” pattern (and why it matters)

In the diagram, GameManager:

  • is a MonoBehaviour
  • stores static references to other managers/entities:
    • ControllerManager, SpawnManager, PlayerEntity, GUIManager, GameSettings, WaveManager, AudioManager, VisualEffectManager, PerkManager, SpecialManager
  • performs setup in Awake() and InitialiseManager()
  • provides high-level app commands: ReturnMainMenu(), RestartGame()

Teaching point: Composition root vs. “God object”

Good intention: central place where references are collected and setup happens.
Risk: if GameManager becomes the place where all gameplay logic lives, it becomes a “God object”.

In this repo, it’s not just wiring: it also holds global state (gameInProgress, mainLoadout). That’s okay, but students should learn the rule:

Let GameManager coordinate systems, not replace them.

Best practice logic coding advice

If you teach from this codebase, recommend:

  • GameManager should set up references and own high-level state transitions (menu → gameplay → results).
  • Wave logic stays in WaveManager.
  • Spawn logic stays in SpawnManager.
  • UI update logic stays in GUIManager.
  • Don’t let GameManager.Update() become “the whole game”.

4) Input architecture in XR: InputManager as an input boundary

The diagram shows:

  • InputManager owns XRIDefaultInputActions customInput
  • lifecycle: Awake(), InitialiseInput(), OnEnable(), OnDisable()
  • it “calls” into ControllerManager and PlayerEntity

Teaching point: Separate “input reading” from “game actions”

In VR, input complexity is high (multiple controllers, gestures, interactions, locomotion modes). Best practice is:

  • Input layer (InputManager): reads hardware/controller state via the Input System / XRI actions.
  • Gameplay layer (PlayerEntity / ControllerManager): exposes intent-based methods like TryFire(), ToggleTool(), Grab(), Teleport(), etc.

That way, you can:

  • remap input without rewriting gameplay logic,
  • simulate input for testing,
  • support multiple control schemes.

XR-specific best practices to teach

  • Avoid doing heavy logic in input callbacks; instead set intent flags or call small methods.
  • Debounce actions (e.g., trigger press vs. hold).
  • Prefer action-based input (XRI default input actions) over polling controller state manually.

5) Encounter loop design: WaveManager + SpawnManager

This is the heart of the gameplay.

WaveManager = “gameplay progression + scoring + pacing”

It owns:

  • waveIndex, spawnIndex
  • playerScore, hostilesDefeated
  • static int missionFails
  • configuration: WaveDetails[] waveArray

And key behaviours:

  • BeginEncounter()
  • EnemyDefeated(type)
  • internal update loop: Update()
  • coroutines: DelaySpawn(), ResetRecentEnemyDefeats()
  • EndGame()

Teaching point: This is a classic game loop controller:

  • Maintains the state machine of the encounter.
  • Emits/requests actions from other systems (spawn next enemy, update UI, play audio).

SpawnManager = “instantiate/pool & place objects”

It owns:

  • Transform[] spawnArray (spawn points)
  • Animator[] doorAnimators (environmental feedback tied to spawns)
  • List<EnemyEntity> enemyList (tracking/pooling)
  • static int activeHostiles (global count)

And spawns:

  • SpawnEnemy(spawnSettings)
  • multiple projectile spawn methods: player/turret/seeker projectiles

Teaching point: separate “decide what spawns” from “how it spawns”:

  • WaveManager should decide what and when.
  • SpawnManager should decide where and how (including pooling, effects, door animations, etc.).

Why this matters in VR best-practice coding

VR performance is unforgiving. Spawning objects can cause:

  • GC allocations → stutter
  • CPU spikes → missed frames → discomfort

So students should be taught to implement:

  • pooling for enemies/projectiles/VFX,
  • simple, data-driven spawn rules,
  • careful use of coroutines/timers over heavy per-frame logic.

This is excellent to teach: your “content” (waves) should be editable without rewriting code.

Best practice suggestions for students:

  • Prefer ScriptableObject assets for more complex wave definitions (versionable, reusable, can include references).
  • Keep the runtime logic generic: “read a definition, execute it”.

7) Cross-cutting systems: UI, audio, VFX, perks, specials

The diagram indicates these interactions:

  • WaveManager triggers:
    • GUIManager for UI updates
    • AudioManager for sound/music
    • SpecialManager for a “special menu”
    • ControllerManager for toggles (plasma cannon)
    • GameSettings for score persistence

Teaching point: avoid direct spaghetti calls as projects grow

Right now, the architecture appears to be direct references (and many are static). That works for coursework scale, but for best practices, teach:

  • Use events/messages for “state changed” notifications:
    • OnWaveStarted(waveIndex)
    • OnEnemyDefeated(enemyType)
    • OnScoreChanged(newScore)
  • UI/audio/VFX subscribe to events rather than being called from everywhere.

This reduces coupling and makes systems independently testable.

8) A best-practice “mental model” students can follow (practical checklist)

When writing logic code for Unity XR, teach students to ask:

  1. Is this code a System or an Entity?
    • If it coordinates gameplay flow: System (Manager).
    • If it lives on a world object: Entity behaviour.
  2. What owns the state?
    • Wave state belongs in WaveManager.
    • Spawn state belongs in SpawnManager.
    • Player combat state belongs in PlayerEntity / weapon controllers.
  3. Where does input end and gameplay begin?
    • InputManager reads input.
    • PlayerEntity executes game actions.
  4. What happens per-frame vs. event-driven?
    • Prefer event-driven.
    • Keep Update() short and predictable.
  5. Will this allocate memory at runtime? (VR performance)
    • Avoid new allocations in Update().
    • Pool frequently spawned objects.
