Direct Button Access in Unity XR (OpenXR)

Tutorials for Unity 6000.0.58f2 + XR Interaction Toolkit 3.0.10, assuming the Starter XR Rig (XR Origin / Action-based by default).

Assumption: You’re using OpenXR with the XR Interaction Toolkit Starter Assets rig, which typically uses XR Controller (Action-based) and the Input System under the hood.

Quick decision guide

  • Option 1 (Action-based XRI): Best default—portable and aligned with the Starter rig.
  • Option 3 (Input System direct): Great for “extra gameplay buttons” without touching Select/Activate.
  • Option 4 (Raw InputDevice): Best for diagnostics / raw values / controller-driven animation.
  • Option 2 (Device-based XRI): Works, but tends to be less flexible/portable under OpenXR.

1) Action-based XRI: Read the same actions the rig uses Recommended

Goal

Read a controller “button” via the XR Controller (Action-based) component already on the Starter rig.

Steps

  1. In the Hierarchy, locate your hand object (e.g., RightHand Controller under XR Origin).
  2. Confirm it has XR Controller (Action-based).
  3. Pick an action to read (common ones): Select, Activate, UI Press.
  4. Add the script below to the same GameObject and assign the controller reference in the Inspector.

Script

using UnityEngine;
using UnityEngine.InputSystem;
using UnityEngine.XR.Interaction.Toolkit;

public class ReadXRIActionBased : MonoBehaviour
{
    [SerializeField] XRController controller; // XR Controller (Action-based)

    void Update()
    {
        if (controller == null) return;

        // Example: read "Activate" (often trigger press)
        InputAction action = controller.activateAction.action;

        if (action != null && action.WasPressedThisFrame())
        {
            Debug.Log("Activate pressed this frame (Action-based XRI).");
        }
    }
}

Notes

  • This reads the same action XRI uses for interactions, so it stays consistent with your rig’s bindings.
  • You can switch to controller.selectAction.action (grip/select) as needed.

2) Device-based XRI: XR Controller (Device-based)

Goal

Use XR Controller (Device-based) and read controller state via “device features” rather than Input Actions.

Steps

  1. Create a test GameObject under XR Origin (or use a spare hand controller object).
  2. Add component: XR Controller (Device-based).
  3. In the component, configure the inputs you care about (trigger, grip, primary button, etc.).
  4. For OpenXR projects, the most reliable “device-based” read is usually to query the XR device directly (see Option 4), using the same hand (XRNode).
Why no single universal code snippet here?
The exact serialized fields and access patterns of the device-based controller component can differ between XRI versions and setups. Under OpenXR, it’s common to configure device-based components for XRI behavior, but read raw values using InputDevice.TryGetFeatureValue when you truly need “direct button state.”

When to use

  • Quick prototypes
  • Minimal Input System setup

Tradeoffs

  • Less flexible than action-based mappings across different OpenXR interaction profiles.

3) Input System direct: Your own action, separate from XRI

Goal

Add a new Input Action (e.g. “PrimaryButton”) and read it in your own script, without modifying XRI Select/Activate.

Steps

  1. Create an Input Actions asset: Create > Input Actions.
  2. Create an Action Map named Gameplay.
  3. Create an Action named PrimaryButton (Action Type: Button).
  4. Add bindings for OpenXR/XRController paths, for example:
    • <XRController>{RightHand}/primaryButton
    • (optional) <XRController>{LeftHand}/primaryButton
  5. Create an InputActionReference to the action and assign it to the script below.

Script

using UnityEngine;
using UnityEngine.InputSystem;

public class ReadInputSystemDirect : MonoBehaviour
{
    [SerializeField] private InputActionReference primaryButton;

    private void OnEnable()
    {
        if (primaryButton != null)
            primaryButton.action.Enable();
    }

    private void OnDisable()
    {
        if (primaryButton != null)
            primaryButton.action.Disable();
    }

    void Update()
    {
        if (primaryButton != null && primaryButton.action.WasPressedThisFrame())
            Debug.Log("Primary button pressed (Input System direct).");
    }
}

Notes

  • Great for “Pause/Menu/Flashlight” style actions that shouldn’t interfere with grab/teleport.
  • Still portable under OpenXR if your bindings include sensible fallbacks.

4) Raw XR device state: UnityEngine.XR InputDevice / XRNode

Goal

Query raw controller state directly from the XR runtime (OpenXR).

Steps

  1. Add the script below to any object (often XR Origin).
  2. Choose XRNode.LeftHand or XRNode.RightHand.
  3. Query features with TryGetFeatureValue (buttons/axes).

Script

using UnityEngine;
using UnityEngine.XR;

public class ReadXRInputDevice : MonoBehaviour
{
    [SerializeField] private XRNode hand = XRNode.RightHand;

    void Update()
    {
        var device = InputDevices.GetDeviceAtXRNode(hand);
        if (!device.isValid)
            return;

        // Button example (A/X on many controllers)
        if (device.TryGetFeatureValue(CommonUsages.primaryButton, out bool primaryDown) && primaryDown)
        {
            Debug.Log($"{hand}: primaryButton is down (raw InputDevice).");
        }

        // Trigger pressed as a button
        if (device.TryGetFeatureValue(CommonUsages.triggerButton, out bool triggerPressed) && triggerPressed)
        {
            Debug.Log($"{hand}: triggerButton is pressed (raw).");
        }

        // Trigger analog value
        if (device.TryGetFeatureValue(CommonUsages.trigger, out float triggerValue) && triggerValue > 0.8f)
        {
            Debug.Log($"{hand}: trigger axis > 0.8 (raw axis).");
        }
    }
}

Notes / Caveats (OpenXR)

  • Not all controllers expose the same CommonUsages consistently.
  • Best used for debugging/animation or when you truly need raw, unabstracted values.
